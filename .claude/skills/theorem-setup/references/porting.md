# Port the build (step 5)

- The builder builds `c`, `c++`, `rust`, `python` and `go` (`docs/project-yaml.md`, "language"). For another language, tell the maintainer that its builder is pending, and stop. A `go` project has the plain build only and gets no theorem statements yet: tell the maintainer.
- The Docker build context is the root of the repository at the commit that `theorem app build` builds (`docs/project-yaml.md`, "The build context"). The `Dockerfile` names each file by its path from the root, for example `COPY .theorem/build.sh $SRC/`. It takes the project's source with `COPY`, for example `COPY . $SRC/<name>`, not with `fetch-commit`. The examples below build from a project folder of theorem-labs/oss-verify. Change their paths when you copy their form.
- C and C++: copy [templates/.theorem/Dockerfile](../../../../templates/.theorem/Dockerfile) and [templates/.theorem/build.sh](../../../../templates/.theorem/build.sh), give them licence lines (step 4.8), and follow `docs/build-contract.md`, "What the Dockerfile must do" and "What build.sh must do". Both sections are written for `projects/<name>/`. In `.theorem/`, the item above replaces the rules of "What the Dockerfile must do" that start from `templates/Dockerfile`, take the source with `fetch-commit` and copy `build.sh` from the project directory. `templates/.theorem/build.sh` replaces the `templates/build.sh` of "What build.sh must do". The hand-written examples are `projects/cjson/` and `tests/fixtures/example/`. Do not copy the form of the other projects and seeds: they are mostly ports of a release build through the helpers of `release-target.sh`.
- Rust: the fuzz targets are the project's cargo-fuzz `[[bin]]`s. Write the build like `seeds/bincode/`. The lock in `.theorem/` is that of the generated `oft-rust-shim` package, not the lock of the fuzz package (`docs/build-contract.md`, "Rust fuzz targets", gives the steps that make it). Get its crates with a `crates` line in `sources`. Do not set `ubsan_checks`.
- Python: the fuzz targets are atheris harnesses. Write the build like `seeds/mdurl/`. Pin each file that `pip install` uses with a `file` line in `sources`. The seed corpus of each fuzz target is an input of its build.
- Go: the OSS-Fuzz Go fuzz targets and its `build.sh`, as they are (`docs/build-contract.md`, "Go fuzz targets"). Write the build like `seeds/go-toml/`. Pin the modules in a `go.lock`, and get them with a `gomodules` line in `sources`. Leave out `sanitizers`, or give `sanitizers: []`.
- Never write a commit id in the `Dockerfile`. Make static riscv64 programs: no shared libraries, no running a compiled program, no network in `build.sh`, and no strip after the link.
- A dependency that needs a patch to build: put the patch in `.theorem/`, and list it in `series`. A patch of a C library that the build declares does not go in `series` (`docs/build-contract.md`, "Build patches"). A change that fixes a bug in the project never goes in `.theorem/`.
- To adopt a seeded project (its `primary_contact` is `n/a`), copy its `projects/<name>/` or its `seeds/<name>/` of theorem-labs/oss-verify into `.theorem/`, and do items 2 to 8 of step 2 of the skill on the copy. Then do steps 2 to 5 of `docs/project-yaml.md`, "Seeded projects", on the files in `.theorem/`. Step 5 there, which makes the fuzz targets obey the rules, is step 4 of this skill.
